# DECISIONS.md — Architecture Decision Log

Records only decisions with significant tradeoffs or that could be re-litigated later.
Format: Decision | Context | Options Considered | Choice | Rationale

---

| # | Decision | Context | Options Considered | Choice | Rationale |
|---|---|---|---|---|---|
| 1 | **Local-first, no cross-device sync in v1** | Early design scope: whether to support multi-device use from launch | (A) Local-only + manual export/import; (B) Firebase Realtime DB sync; (C) Supabase sync; (D) iCloud/GDrive sync | **A — Local-only** | Sync requires auth, increases attack surface, adds infrastructure cost, and conflicts with the offline-first promise. Export/import satisfies the backup need. Sync deferred to v2 as an optional layer. Source: `BLUEPRINT.md § I.3`. |
| 2 | **Split storage: IndexedDB for events, localStorage for actions/settings** | Events need efficient date-range queries and are written frequently. Actions are small, rarely change, and need synchronous reads during rendering. | (A) All in IndexedDB; (B) All in localStorage; (C) Split by access pattern | **C — Split** | IndexedDB handles range queries on `occurred_at` efficiently via indexes. localStorage provides synchronous reads for actions (needed in render path). Mixing them in IndexedDB adds schema complexity without benefit for small action payloads. Source: `BLUEPRINT.md § II.2`. |
| 3 | **Denormalize `action_name_snapshot`, `action_icon_snapshot`, `action_color_snapshot` into Event** | If an Action is renamed, re-colored, or archived after logging, historical Event rows should still display the original identity. | (A) JOIN Action to Event at render time; (B) Snapshot all display fields at log time | **B — Snapshot** | JOIN fails silently if Action is archived or deleted. Snapshot preserves historical integrity with minimal storage overhead (~100 bytes per event). The accepted tradeoff is data redundancy. Source: `BLUEPRINT.md § II.2`. |
| 4 | **Action-first dashboard: suggestion tiles primary, timeline secondary** | Dashboard design risk: history view dominates the screen, burying the logging CTA. | (A) Timeline-first (history prominent, CTA secondary); (B) Action-first (suggestion tiles prominent, timeline below the fold) | **B — Action-first** | UX Principle A: "Recording must be easier than deferring." The critical-path action (log something) must be the first affordance on screen. Timeline is accessible by scrolling. Source: `BLUEPRINT.md § II.1`. |
| 5 | **No confirmation dialog on log tap; save immediately with undo** | Principle A demands zero friction. Accidental logs are possible. Two options address accidental taps differently. | (A) Confirmation dialog: "Log [action]? Yes / No"; (B) Save immediately + 3s undo toast | **B — Save + undo** | Confirmation dialogs violate the one-tap promise and train users to hesitate. Undo (3s toast) handles accidental logs with equal safety and zero confirmation overhead. Users who don't need undo ignore the toast. Source: `BLUEPRINT.md § II.4`. |
| 6 | **Remove bottom navigation bar; use top-edge navigation only** | Original design included a bottom navigation bar. Revised design removed it. | (A) Keep bottom nav (Android convention); (B) Top-edge nav only (viewport-efficient) | **B — Top-edge only** | Bottom nav occupies 56px+ of viewport space that belongs to the TapTile grid. Top-edge nav saves that real estate for the logging surface. Breaks Android Material nav convention but acceptable given the custom "field instrument" aesthetic. Source: `BLUEPRINT.md § II.1`. |
| 7 | **React 18 + TypeScript + Vite 5 as tech stack** | Tech stack not specified in design documents. Inferred from design system complexity and interaction patterns. | (A) Vanilla JS + Vite (smallest bundle); (B) React 18 + TypeScript + Vite 5; (C) Vue 3 + TypeScript + Vite; (D) Svelte + Vite | **B — React + TS + Vite** | Repeated TapTile/ActionCard components benefit from React's component model. TypeScript enforces Action/Event interface contracts, preventing IDB schema drift. vite-plugin-pwa provides the cleanest Workbox integration path. **⚠️ This decision was made by the AI project agent, not specified by the developer. Revise if the developer has a different preference — update SPEC.md § I before any code.** |
| 8 | **`idb` library (Jake Archibald) for IndexedDB access** | Need a promise-based wrapper; raw IndexedDB API is verbose. | (A) Raw `indexedDB` API; (B) `idb` (~2KB, Promise-based); (C) Dexie.js (~20KB, full ORM) | **B — idb** | `idb` wraps IndexedDB in promises with minimal overhead. Dexie is a full ORM — unnecessary for a single `events` object store. Raw API is too verbose for readable migrations. |
| 9 | **Zustand for UI state management** | Need to manage active view, drawer state, undo stack, and toasts centrally. | (A) React Context + useReducer; (B) Zustand; (C) Jotai | **B — Zustand** | TapTiles can fire at high frequency; Zustand avoids Context re-render cascades. Simple, flat API with minimal boilerplate. Good DevTools support. No dependency on React's concurrent scheduling for state updates. |
| 10 | **Lucide React as icon library** | Blueprint requires "thư viện ổn định" (stable library). Icon library is used for Action template icons — must be stable, comprehensive, and treeshakeable. | (A) Google Material Icons; (B) Lucide React; (C) Phosphor Icons; (D) Heroicons | **B — Lucide React** | MIT licensed; 1000+ icons; tree-shakeable (only imported icons in bundle); stable API with rare breaking changes; React-native integration; actively maintained. Best match for "stable library" requirement. |
| 11 | **Soft-delete actions via `archived_at` field** | Deleting an action would orphan historical events referencing that `action_id`. | (A) Hard delete + null out `action_id` in orphaned events; (B) Soft-delete with `archived_at` timestamp | **B — Soft-delete** | Archived actions never show in suggestions or library but their events remain intact and queryable. `action_name_snapshot` ensures display is not broken even for archived actions. Preserves data integrity without cascading deletes. |
| 12 | **Session-only undo stack; not persisted across restarts** | Undo is for immediate mistakes. Question: should undo survive app restart? | (A) Persist undo stack to localStorage across sessions; (B) Session-only (in-memory; cleared on reload) | **B — Session-only** | Cross-session undo is confusing and unexpected ("I logged this 2 hours ago and I can still undo it?"). Session-only aligns with user mental model of undo as an immediate safety net, not a history browser. |
| 13 | **Suggestion cold-start: fall back to pinned + `sort_order` when history is sparse** | Scoring algorithm requires historical data. New users have none; scores are meaningless. | (A) Show empty suggestion area; (B) Show all actions sorted alphabetically; (C) Fallback to pinned first, then `sort_order` | **C — Pinned + sort_order** | Empty suggestions offer no value. Alphabetical order ignores user intent. Pinned + sort_order respects the user's own prioritization signals (they pinned their most important actions). Apply scoring only when ≥ 3 events exist in the last 7 days. |
| 14 | **Google Fonts + Workbox cache-first for font loading** | Fonts (Space Grotesk, JetBrains Mono, Newsreader) are critical for the design system and must work offline. | (A) Self-host WOFF2 files in `src/assets/fonts/`; (B) Google Fonts CDN + Workbox `CacheFirst` strategy | **B — Google Fonts + Workbox** | Self-hosting requires downloading files and increases repo size. Workbox CacheFirst provides full offline support after first visit. Simpler development setup. Note: self-hosting is preferable for production CDN-independence; revisit before launch. |
